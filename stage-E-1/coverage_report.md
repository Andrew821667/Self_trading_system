## Обнаруженное ограничение: не антибот, а сетевая политика этой сессии

Ожидалось, что практическим ограничением будут антибот-механизмы
e-disclosure.ru или глубина архива Банка России/Мосбиржи (как и
предполагал владелец в задании). Фактическая причина в этой сессии —
раньше и жёстче: **исходящий сетевой доступ из этого окружения Claude Code
разрешён только для узкого allowlist (GitHub, реестры пакетов npm/PyPI/
crates, инфраструктура Anthropic)**. Инструмент постраничного получения
контента (WebFetch) возвращает `EGRESS_BLOCKED` для любого внешнего домена
вне этого списка — проверено не только на целевых источниках, но и на
нейтральном контрольном домене (en.wikipedia.org), который тоже заблокирован,
тогда как github.com — доступен. Это подтверждает: блокировка на уровне
политики окружения, а не на уровне конкретного сайта.

Проверено и заблокировано (`EGRESS_BLOCKED`):

| Источник | URL | Результат |
|---|---|---|
| Центр раскрытия корпоративной информации | e-disclosure.ru, www.e-disclosure.ru | заблокирован политикой |
| Банк России | cbr.ru, www.cbr.ru | заблокирован политикой |
| Московская биржа | moex.com | заблокирован политикой |
| ISS API | iss.moex.com | заблокирован политикой (в т.ч. напрямую через curl — `CONNECT tunnel failed, 403`) |
| Контроль (ожидаемо доступен) | en.wikipedia.org | заблокирован политикой — подтверждает, что блок общий, а не точечный |
| Контроль (ожидаемо доступен) | github.com | доступен — allowlist работает избирательно, не является общим сбоем |

`WebSearch` (отдельный, серверный инструмент — поиск и суммирование
выполняются на стороне Anthropic, а не фетчем из этой сессии) при этом
работает и возвращает сниппеты по релевантным запросам. Но сниппет
поисковой выдачи — это пересказ третьей стороны, не первичный документ: он
не даёт ни проверяемого `sha256` реального файла, ни надёжной
`published_at`, ни текста, пригодного для слепой классификации по
чек-листу. Использовать его как замену `documents/<event_id>/*` в этом
пайплайне значило бы подменить требование ТЗ 6.1/5.3 (реальный документ,
хеш, `first_seen_at`) непроверяемым пересказом — это прямо запрещено
принципом "агент не достраивает юридически существенный факт
предположением" (чек-лист, раздел D).

## Что нужно, чтобы снять блокер

Это настройка окружения, которую меняет владелец сессии, а не ограничение
кода или протокола сбора. Варианты (не решаю сам — см. вопрос владельцу в
диалоге):

1. Расширить allowlist сетевой политики этого окружения Claude Code
   (e-disclosure.ru, cbr.ru, moex.com, iss.moex.com) — тогда сбор
   продолжается в этой же сессии тем же кодом/протоколом. **Выбрано
   владельцем 2026-08-22.** Точный путь (claude.ai/code → значок облака в
   строке над полем ввода → шестерёнка настроек текущего окружения →
   Network access → Custom):
   ```text
   e-disclosure.ru
   *.e-disclosure.ru
   cbr.ru
   *.cbr.ru
   moex.com
   *.moex.com
   ```
   Важно отметить чекбокс «Also include default list of common package
   managers» (или продублировать реестры pypi/npm в списке вручную) —
   иначе после перехода с Trusted на Custom сборка проекта (`uv sync`)
   потеряет доступ к PyPI. Изменение применяется к сессиям окружения;
   если после сохранения повторный запрос всё ещё возвращает
   `EGRESS_BLOCKED`, вероятно нужна новая сессия в этом окружении, а не
   ретрай в текущей.
2. Собрать документы в окружении без этого ограничения и передать в
   репозиторий тем же способом, что и `edge_thesis_R0_v1.md` /
   `event_checklist_E1_v1.md` в этом же шаге — с проверкой хеша перед
   коммитом.
3. Дать точечный, разрешённый способ доступа (например, экспорт/API-ключ
   стороннего агрегатора, если такой уже используется владельцем).

До выбора варианта Фаза A физически не может продвинуться дальше нулевого
покрытия — это не вопрос усилий или количества попыток запроса.

## Повторная проверка после расширения allowlist (2026-08-22)

Владелец расширил Network access окружения до Custom с доменами из раздела
выше. Повторная проверка через прямой HTTP (curl) и через WebFetch:

| Источник | curl (сетевой egress сессии) | WebFetch | Вывод |
|---|---|---|---|
| cbr.ru / www.cbr.ru | ✅ `HTTP 200` | ❌ `EGRESS_BLOCKED` | доступен через прямой HTTP |
| moex.com → www.moex.com | ✅ `HTTP 301` → `HTTP 200` | не проверялся повторно | доступен через прямой HTTP |
| iss.moex.com (ISS API) | ✅ реальные рыночные данные получены (доска TQBR) | ❌ `EGRESS_BLOCKED` (первая попытка) | доступен через прямой HTTP, подтверждено содержимым |
| e-disclosure.ru / www.e-disclosure.ru | ⚠️ `HTTP 200`, но антибот-заглушка (см. ниже) | ❌ `EGRESS_BLOCKED` | сетевой блок снят, но сайт отдаёт защиту от ботов |

**Важное расхождение инструментов:** `WebFetch` продолжает возвращать
`EGRESS_BLOCKED` даже для cbr.ru после обновления allowlist, тогда как
`curl` из Bash проходит. Вывод: `WebFetch` не использует сетевую политику
этого окружения (Custom allowlist) — это отдельный, управляемый Anthropic
канал со своим, не настраиваемым из окружения списком доменов. Рабочий
инструмент для этого источника — прямой HTTP-запрос из Bash (`curl`), не
`WebFetch`. Это техническая деталь для дальнейшей работы, не вопрос к
владельцу.

### e-disclosure.ru: сетевой блок снят, но сайт защищён антиботом

`curl` с реалистичным `User-Agent` получает `HTTP 200` на `/`, `/poisk/`,
`/search/`, `/portal/`, но во всех случаях — один и тот же контент (~368 КБ):
HTML-заглушка со спиннером и `<noscript>`-редиректом на служебный путь
(`/exhkqyad`), то есть JS-проверка перед выдачей реального контента.
Путь `/api/` отдаёт `307` с `Set-Cookie: spid=…; spsc=…` (типичные
антибот-cookie для fingerprint/proof-of-work проверки) и редиректит сам на
себя — без исполнения JS-кода этот цикл не проходится.

Попытка обойти через headless-браузер (Chromium уже установлен в
окружении, добавлен пакет `playwright` временно через
`uv run --with playwright`, без изменения зависимостей проекта):
подключение через прокси окружения (`HTTPS_PROXY`) для Chromium даёт
`net::ERR_CONNECTION_RESET` — причём это воспроизводится и на cbr.ru,
который прекрасно открывается через `curl`. Значит, проблема не в
антиботе e-disclosure.ru, а в интеграции Chromium с прокси именно в этой
песочнице (другой сетевой стек/TLS-отпечаток, который прокси или сама
цель обрывает). Это не доказательство того, что headless-браузер не смог
бы пройти антибот e-disclosure.ru — вопрос остался неисследованным,
потому что браузер не смог подключиться вообще ни к одному сайту через
прокси этой сессии.

**Оценка, не факт:** дальнейшая отладка Chromium+прокси в этой песочнице
не гарантирует результата даже при успехе — антибот-провайдеры такого типа
часто дополнительно детектируют headless-браузеры (флаг
`navigator.webdriver`, TLS/JA3-отпечаток, репутация дата-центрового IP).
Обычный браузер под управлением человека (то есть локальная машина
владельца) проходит такую защиту естественным образом.

**Вывод:** применяю пункт 3 текущего задания по смыслу, а не по букве —
формально это не `403 host_not_allowed` (сеть открыта, отвечает сайт), но
результат для конвейера тот же: ни один доступный в этой сессии инструмент
не может получить реальный документ с e-disclosure.ru. Раз это первичный,
не заменяемый источник самих текстов предложений/требований о выкупе (в
отличие от cbr.ru/moex.com, которые дают справочные данные, но не тексты
существенных фактов), собирать документы с e-disclosure.ru предлагается
на локальной машине владельца (обычный браузер, вручную или обычным
скриптом без прокси-ограничений) и передавать в репозиторий тем же
способом, что и уже переданные `edge_thesis_R0_v1.md` /
`event_checklist_E1_v1.md` — с проверкой `sha256` и `published_at` перед
коммитом в `stage-E-1/documents/`.

Инвентарь (`inventory/events.jsonl`) остаётся пустым: строки по
voluntary_or_mandatory_offer, squeeze_out_request_95 и forced_buyback
структурно требуют текста самого предложения/требования (цена, ценовая
база, банк-гарант, приобретатель) — без e-disclosure.ru эти поля неоткуда
взять достоверно. `buyback_art_75_76` частично пересекается с решениями
Мосбиржи о делистинге (`www.moex.com/ru/news/?ncat=104`, реально доступен,
содержит формулировки о включении/исключении бумаг из Списка) — это
годится как триггер/наводка на конкретное событие, но не как источник
цены/условий выкупа, которые всё равно публикуются через раскрытие
информации. Ни одна строка не добавлена на основании одной лишь наводки
без первичного документа.

## Обновление 2026-08-23: headless-Chromium (таймбокс), cbr.ru, альтернативные агентства

### 1. Headless-Chromium через прокси — таймбокс исчерпан, брошено

Дополнительная диагностика (net-log Chromium): в одном и том же вызове
(один и тот же порт `HTTPS_PROXY`, одна и та же секунда) `curl` получает
`HTTP 200` на `www.cbr.ru`, а Chromium с тем же прокси — то `net::
ERR_CONNECTION_RESET`, то один раз явный ответ прокси `403 Forbidden:
"request blocked: no rule or allowlist entry allows host www.…"`.
Воспроизведено с отключённым preconnect/prediction, без
`--ignore-certificate-errors`, с `--proxy-server` вместо Playwright API —
результат тот же. Вывод: это несовместимость headless Chromium с
прокси-слоем именно этой песочницы (не антибот конкретного сайта — тот же
сбой на cbr.ru, который прекрасно открывается через `curl`). Не критический
путь, дальше не отлаживается; `curl` остаётся рабочим инструментом.

## Обновление 2026-08-23 (сессия 2): выдача поиска не получена, но найдены три рабочих механизма

Итог по каркасу: **инвентарь всё ещё 0 строк** по всем 4 типам и всем
годам. Ниже — что именно найдено и почему выдачу так и не удалось
получить в этой сессии; это не пропуск проверки, а исчерпанный (и
задокументированный) путь.

### Найдено: три реальных, воспроизводимых механизма

1. **Актуальная таксономия подтверждена на боевом e-disclosure.ru прямо
   сейчас.** Коды `181`/`182`/`184`/`185`/`245`/`246` (та же нумерация,
   что и на SKRIN — это единая регуляторная нумерация Банка России, не
   внутренний ID конкретного агентства) присутствуют в форме поиска
   `https://www.e-disclosure.ru/poisk-po-soobshheniyam` на момент проверки.
2. **Антибот обходится для POST-запросов с заголовком
   `X-Requested-With: XMLHttpRequest`.** Обычный GET на любой путь
   отдаёт JS-заглушку (~368 КБ, спиннер + antibot-cookie `spid`/`spsc`,
   как и раньше). Тот же путь, но POST с этим заголовком и `Referer`,
   отдаёт **настоящую страницу сайта** (~718 КБ, реальные заголовки,
   реальная лента новостей с сегодняшней датой) — antibot пропускает
   такие запросы. Это первый воспроизведённый случай, когда e-disclosure.ru
   отдал живой (не архивный) контент в этой сессии.
3. **web.archive.org реально хранит и отдаёт читаемые архивные копии
   отдельных сообщений** `portal/event.aspx?EventId=...` в обход антибота
   (антибот применяется только на live-сайте, архивная копия отдаётся
   напрямую с инфраструктуры Internet Archive). Подтверждено на реальном
   примере: сообщение ПАО НК «РуссНефть» от 10.08.2021 — полный текст,
   ОГРН/ИНН, тип сообщения, содержание. CDX API
   (`web.archive.org/cdx/search/cdx`) даёт список архивных снимков по
   маске URL — но **не по содержимому**, поэтому им нельзя напрямую
   отфильтровать по типу сообщения.

### Не получилось: сама выдача результатов поиска

POST на `/poisk-po-soobshheniyam` (собственный URL формы, как в архивных
версиях 2013 и 2022 года) с полным набором полей текущей формы
(`eventTypeCheckboxGroup`, `districtsCheckboxGroup` — поле переименовано
с `regionsCheckboxGroup` при редизайне сайта, `branchesCheckboxGroup`,
`dateStart`/`dateFinish`, `immediate`, `radReg`, `radView`) даёт
**побайтово идентичный ответ (718480 байт) независимо от параметров** —
значит, сервер не обрабатывает эти POST как поисковый запрос вообще.
Сайт использует RequireJS (`/src/js/require.min.js`) для загрузки
логики страницы отдельными модулями; реальный AJAX-эндпоинт выдачи
находится не по адресу самой страницы (в отличие от версий 2013/2022) и
не был найден за разумное время — поиск конкретного модуля/маршрута
прекращён, чтобы не повторить историю с Chromium-прокси.

**Практический вывод для следующего шага (важно для второй/локальной
сессии):** ничего из вышеперечисленного реверс-инжинирить не нужно.
Обычный браузер выполнит JS страницы как задумано, антибот-проверку
пройдёт штатно (она рассчитана именно на человека с браузером), и форма

185 (названия — «Поступление эмитенту добровольного/обязательного
предложения…», «…уведомления о праве требовать выкупа…», «…требования о

   корректный pending, а не дефект парсера.

## Почему извлечение не доводится до 100% здесь

Это сознательная граница, а не недоработка. По ТЗ 6.3–6.5 структурная
экстракция — предмет Stage E1: с валидацией схемы, закреплением пары
`extraction_model`/`prompt_version`, золотым регрессионным набором и
ручной проверкой эталонов. Подменять это регулярками в Фазе A нельзя —
получилась бы незафиксированная, непроверяемая экстракция в основании
всего дальнейшего исследования. Фазе A нужен **индекс** событий, и он
собран; остальное честно помечено `pending_fields`, а событие с непустым
`pending_fields` не допускается к классификации.

## Дефекты, найденные в собственном коде по ходу

- `PAGEN_1` вместо `PAGEN_2` — недосчёт 83 строк (исправлено до публикации цифр).
- `Decimal("22,18")` — русская десятичная запятая роняла разбор цены целиком
  (исправлено: 69 → 112).
- Приобретателем бывает физлицо, а не организация (исправлено: 34 → 60).
- `urlopen(timeout=...)` не сработал на полуоткрытом сокете, загрузка зависла
  на 742-м документе (добавлен `socket.setdefaulttimeout`).

# Ревизия 2026-08-24: 519 событий из 812 исключены из семейства

Проверка собранного по текстам документов (а не по названиям типов
сообщений) показала, что моя привязка кодов 1080045 / 4005185 к
`buyback_art_75_76` **была неверной**. Инвентарь исправлен.

## Что показала проверка норм в текстах

| Тип сообщения (код) | Всего | ст. 72 | ст. 75/76 | норма не названа |
|---|---|---|---|---|
| Приобретение эмитентом собственных акций (1080045) | 473 | 248 | 22 | 203 |
| Принятие решения о приобретении размещённых акций (4005185) | 46 | 8 | 2 | 36 |

Две независимые причины исключить их обе:

1. **Норма не та.** 256 событий прямо ссылаются на **ст. 72** — это
   дискреционный корпоративный buyback: цена не определена законом,
   обязанности выкупить у всех нет. Это ровно противоположно механизму,
   на котором стоит тезис (обязанность купить по формульной цене в
   известный срок). Ст. 75/76 называют только 24 из 519.
2. **Событие не то.** Тип 1080045 — это **отчёт постфактум** о том, что
   приобретение уже состоялось, а не объявление предстоящей процедуры.
   Спреда «объявление → юридический дедлайн», который и есть предмет
   тезиса, в таком сообщении по определению нет.

Исключённые строки не удалены — они лежат в
`stage-E-1/inventory/out_of_family.jsonl` вместе со скачанными
документами, чтобы запись о сборе оставалась полной и проверяемой.

Рост по приобретателю и гаранту — не подгонка, а исправление дефекта: у
требований о выкупе пункт называется иначе («лицо, направившее уведомление
о праве требовать выкуп… или требование о выкупе»), и часть эмитентов
пишет ответ не после двоеточия, а на следующих строках. Оба случая теперь
обрабатываются. Падение `isin` — следствие смены знаменателя: ISIN чаще
указывался как раз в исключённых сообщениях о собственных акциях.

## `buyback_art_75_76` = 0: почему и что нужно

Прямого типа сообщения под выкуп по ст. 75–76 в таксономии агентства
**нет**. Право требовать выкупа возникает из решения общего собрания
(реорганизация, крупная сделка, делистинг), которое раскрывается в общей
категории «Решения общих собраний акционеров» — тысячи сообщений, не
отфильтровываемых по типу. Ближайшие косвенные триггеры в таксономии:
`1079921` (исключение бумаг из списка торгов — делистинг) и `1079194`
(заявление в ЕГРЮЛ о реорганизации); их пришлось бы сопоставлять с
уведомлениями о праве выкупа. Это отдельная работа, а не быстрая правка,
и она не сделана.

## `forced_buyback` = 0: почему

Ст. 84.7 и 84.8 в шаблоне сообщения не разделяются — обе фигурируют в
одной формулировке («уведомление о праве требовать выкуп … или
требование о выкупе»). Из 93 сообщений типа 1079969 на ст. 84.8 прямо
ссылаются 8. Разделение — задача экстракции по тексту (Stage E1), не
индексации.

Эмпирическая проверка: самая ранняя дата события во всём собранном —

# Реализуемость по ликвидности (2026-08-24) — приёмочный критерий E-1

ТЗ требует для приёмки E-1 «оценена реализуемость по ликвидности при
капитале владельца». Проверка выполнена: `scripts/check_tradability.py`,
результат — `stage-E-1/inventory/tradability.csv`.

Метод: сопоставление **по ИНН эмитента** со справочником бумаг Московской
биржи (ISS API отдаёт `emitent_inn`), то есть точный join, а не сходство
названий. Справочник: 2515 бумаг, 757 ИНН эмитентов.

| | событий | доля |
|---|---|---|
| Всего в инвентаре | 293 | 100% |
| Эмитент **есть** в справочнике MOEX | **25** | 8% |
| Эмитента в MOEX **нет вообще** | **268** | **91%** |

## Что это означает

91% собранных событий — непубличные АО, акции которых на бирже не
обращаются. Купить их на рынке нельзя, значит тезис («купить с дисконтом к
почти определённой выплате и сдать в процедуру») к ним **неприменим
независимо от юридического механизма**. Для исследования это не «слабые
наблюдения», а наблюдения не из той генеральной совокупности.

Реально пригодных событий — **25 за 4,4 года**, то есть примерно 5–6 в
год, ДО применения чек-листа. А чек-лист отфильтрует ещё: Д-7 (ликвидность
не пропускает позицию), Д-10 (АПК и связанные с деятельностью владельца),
и требование ≥7 из 9 признаков П.

Среди этих 25 — узнаваемые истории: «Детский мир», «Квадра», «ЭЛ5-Энерго»,
«Кокс», «ТНС энерго», РОСБАНК, Ашинский метзавод, «ИНГРАД», Калужская
сбытовая, CarMoney. То есть события правильного типа, их просто мало.

## Важная оговорка: это смещение источника, а не свойство рынка

Вывод «в семействе мало торгуемых событий» из этих цифр **не следует**.
AZIPI — небольшое агентство, обслуживающее преимущественно мелкие
региональные АО. Публичные эмитенты, которых как раз и можно торговать,
раскрываются в основном через Интерфакс (`e-disclosure.ru`, ~90%
листингованных эмитентов), доступ к которому в этой среде закрыт
антиботом. Иначе говоря, **выборка систематически смещена против
торгуемых эмитентов** ровно тем способом, который делает её непригодной
для вердикта.

Настоящее число торгуемых событий E-1 за 2019–2025 почти наверняка
существенно больше 25 — но лежит у Интерфакса.

## Следствие для плана

Вердикт E-1 на текущих данных выносить нельзя: 25 наблюдений за 4,4 года
при неизвестном смещении отбора не дают статистической базы ни для
подтверждения, ни для опровержения тезиса. Это ограничение данных, а не
результат проверки тезиса — и путать одно с другим нельзя (вердикт «не
подтверждён» по ТЗ закрывает семейство навсегда).

# Пилот на торгуемых событиях (2026-08-24): ликвидность не является узким местом

Проверен дисквалификатор **Д-7** («ликвидность не пропускает позицию: вход
или выход > нескольких дневных объёмов при капитале владельца») на всех 25
торгуемых событиях. Скрипт `scripts/assess_liquidity.py`, результат —
`stage-E-1/inventory/liquidity.csv`.

Метод: медианный дневной оборот в рублях за 90 календарных дней **строго до
даты объявления** (сам день события исключён), против позиции 200 000 ₽
(20% от капитала 1 млн ₽, т.е. пять позиций). Порог — 3 дневных оборота.

**Слепой протокол соблюдён:** запрашивались только доэвентные данные.
Ни цены, ни объёмы на дату события и после неё не запрашивались, поэтому об
исходах процедур отсюда ничего не узнать — это вход, доступный принимающему
решение в момент объявления, а не исход.

## Результат

| | событий |
|---|---|
| Торгуемых событий | 25 |
| **Проходят Д-7** | **21** |
| Не проходят | 4 |

Не проходят: KMTZ (Косогорский метзавод), KOKS («Кокс»), ELIB (ЭЛСИБ) —
торгов до события не было вообще; RTSB (ТНС энерго Ростов) — 5,8 дневных
оборота на позицию.

У большинства прошедших запас огромный: «Детский мир» — 0,02 дневного
оборота, Ашинский метзавод — 0,01, «Европейская Электротехника» — 0,01.
То есть при капитале 1 млн ₽ **ликвидность не связывает**: это прямое
подтверждение довода C-1 тезиса («малый капитал как пропуск в нишу»).

## Что это значит для вердикта

Узкое место — **не ликвидность, а размер выборки**. 21 пригодное событие за
4,4 года ≈ 5 в год. Для статистического вердикта (R3-B: доверительные
интервалы, permutation p-value, разбиение по подпериодам, плацебо-контроль)
этого категорически мало, и вдобавок выборка смещена источником (см.
предыдущий раздел).

Дисквалификатор Д-10 (АПК и связанные с деятельностью владельца) на этой
подвыборке почти не работает: металлургия, энергетика, ритейл, банки,
транспорт, микрофинансы — АПК среди них нет.

Признаки П-1…П-9 на этих данных не проверяются: они требуют фактов из
приложенных к предложению документов (банковская гарантия, ценовая база,
история приобретателя), которых в тексте сообщения нет. Формальная
классификация не запускалась намеренно — валидатор её и не пропустит, пока
у события непустой `pending_fields` (правило D чек-листа: неполные данные →
дисквалифицировано).

# Найден путь к недостающим документам

`https://www.disclosure.ru/issuer/<ИНН>/` — постраничный архив раскрытия по
эмитенту, где среди «прочих документов» лежат **сами тексты процедур**:
проверено на АО «НКГФ» (ИНН 0264011929) — «Обязательное предложение о
приобретении акций» (19,7 МБ) и «Требование о выкупе акций» (12,1 МБ),
скачиваются по ссылке `GetFileMD5?md5=…` без антибота. Архивы годовых
отчётов там уходят до 2011 года, то есть глубина заметно больше, чем у
AZIPI.

Два ограничения: файлы приходят **RAR-архивами**, а распаковщика RAR в этой
среде нет; и АК&М обслуживает только своих клиентов — «Детский мир»,
например, отдаёт пустую страницу. Но для тех эмитентов, что там есть, это
закрывает пробелы №2 (условия предложения) и №3 (ценовая база из отчёта
оценщика).

# Делистинги MOEX как триггеры ст. 75–76 (2026-08-24)

Агентства не дали ни одного события семейства `buyback_art_75_76` —
подходящего типа сообщения в их таксономии нет. Найден обходной источник:
**история листинга Московской биржи** (ISS `history/.../listing`), где у
каждой бумаги записаны окна котирования по каждому режиму торгов. Бумага,
у которой закрылось последнее окно и которая больше не торгуется, —
делистинг, а делистинг есть прямое основание права требовать выкупа по
ст. 75.

Скрипт `scripts/collect_delistings.py`, результат —
`stage-E-1/inventory/delisting_triggers.csv`.

## Результат: 73 делистинга акций, 64 эмитента, 2019–2025

| Год | 2019 | 2020 | 2021 | 2022 | 2023 | 2024 | 2025 | итого |
|---|---|---|---|---|---|---|---|---|
| Делистингов акций | 11 | 6 | 13 | 22 | 12 | 5 | 4 | **73** |

Отфильтровано: паи ПИФов, депозитарные расписки, ипотечные сертификаты —
права требовать выкупа по ст. 75–76 они не порождают. Из 323 бумаг,
прекративших торговаться в этот период, акциями являются 73.

## Чем этот источник лучше агентского

1. **Покрывает пропущенные годы.** 2019 и 2020 представлены (11 и 6
   событий) — те самые годы, куда архив AZIPI не достаёт.
2. **По построению только торгуемые бумаги.** Проблемы «91% эмитентов нет
   на бирже» здесь не существует: в выборку попадает лишь то, что
   котировалось.
3. **Машиночитаемо и датировано** — без разбора текстов и без антибота.

## Чем это НЕ является

Дата делистинга — **триггер, а не само событие E-1**. Право требовать
выкупа возникает из решения общего собрания, а у самого выкупа своя цена и
свои сроки, раскрываемые отдельно. Эти 73 строки говорят, у какого эмитента
и на какую дату искать документы, — то есть превращают поиск в адресный
вместо сплошного перебора архива.

Следующий шаг по ним — сопоставить каждый делистинг с раскрытием эмитента
(решение собрания о делистинге + уведомление о праве требовать выкупа), где
и лежат цена и условия. Для эмитентов, обслуживаемых АК&М, это
`disclosure.ru/issuer/<ИНН>/`; для остальных — Интерфакс.

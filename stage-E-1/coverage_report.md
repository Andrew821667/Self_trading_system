## Обнаруженное ограничение: не антибот, а сетевая политика этой сессии

Ожидалось, что практическим ограничением будут антибот-механизмы
e-disclosure.ru или глубина архива Банка России/Мосбиржи (как и
предполагал владелец в задании). Фактическая причина в этой сессии —
раньше и жёстче: **исходящий сетевой доступ из этого окружения Claude Code
разрешён только для узкого allowlist (GitHub, реестры пакетов npm/PyPI/
crates, инфраструктура Anthropic)**. Инструмент постраничного получения
контента (WebFetch) возвращает `EGRESS_BLOCKED` для любого внешнего домена
вне этого списка — проверено не только на целевых источниках, но и на
нейтральном контрольном домене (en.wikipedia.org), который тоже заблокирован,
тогда как github.com — доступен. Это подтверждает: блокировка на уровне
политики окружения, а не на уровне конкретного сайта.

Проверено и заблокировано (`EGRESS_BLOCKED`):

| Источник | URL | Результат |
|---|---|---|
| Центр раскрытия корпоративной информации | e-disclosure.ru, www.e-disclosure.ru | заблокирован политикой |
| Банк России | cbr.ru, www.cbr.ru | заблокирован политикой |
| Московская биржа | moex.com | заблокирован политикой |
| ISS API | iss.moex.com | заблокирован политикой (в т.ч. напрямую через curl — `CONNECT tunnel failed, 403`) |
| Контроль (ожидаемо доступен) | en.wikipedia.org | заблокирован политикой — подтверждает, что блок общий, а не точечный |
| Контроль (ожидаемо доступен) | github.com | доступен — allowlist работает избирательно, не является общим сбоем |

`WebSearch` (отдельный, серверный инструмент — поиск и суммирование
выполняются на стороне Anthropic, а не фетчем из этой сессии) при этом
работает и возвращает сниппеты по релевантным запросам. Но сниппет
поисковой выдачи — это пересказ третьей стороны, не первичный документ: он
не даёт ни проверяемого `sha256` реального файла, ни надёжной
`published_at`, ни текста, пригодного для слепой классификации по
чек-листу. Использовать его как замену `documents/<event_id>/*` в этом
пайплайне значило бы подменить требование ТЗ 6.1/5.3 (реальный документ,
хеш, `first_seen_at`) непроверяемым пересказом — это прямо запрещено
принципом "агент не достраивает юридически существенный факт
предположением" (чек-лист, раздел D).

## Что нужно, чтобы снять блокер

Это настройка окружения, которую меняет владелец сессии, а не ограничение
кода или протокола сбора. Варианты (не решаю сам — см. вопрос владельцу в
диалоге):

1. Расширить allowlist сетевой политики этого окружения Claude Code
   (e-disclosure.ru, cbr.ru, moex.com, iss.moex.com) — тогда сбор
   продолжается в этой же сессии тем же кодом/протоколом. **Выбрано
   владельцем 2026-08-22.** Точный путь (claude.ai/code → значок облака в
   строке над полем ввода → шестерёнка настроек текущего окружения →
   Network access → Custom):
   ```text
   e-disclosure.ru
   *.e-disclosure.ru
   cbr.ru
   *.cbr.ru
   moex.com
   *.moex.com
   ```
   Важно отметить чекбокс «Also include default list of common package
   managers» (или продублировать реестры pypi/npm в списке вручную) —
   иначе после перехода с Trusted на Custom сборка проекта (`uv sync`)
   потеряет доступ к PyPI. Изменение применяется к сессиям окружения;
   если после сохранения повторный запрос всё ещё возвращает
   `EGRESS_BLOCKED`, вероятно нужна новая сессия в этом окружении, а не
   ретрай в текущей.
2. Собрать документы в окружении без этого ограничения и передать в
   репозиторий тем же способом, что и `edge_thesis_R0_v1.md` /
   `event_checklist_E1_v1.md` в этом же шаге — с проверкой хеша перед
   коммитом.
3. Дать точечный, разрешённый способ доступа (например, экспорт/API-ключ
   стороннего агрегатора, если такой уже используется владельцем).

До выбора варианта Фаза A физически не может продвинуться дальше нулевого
покрытия — это не вопрос усилий или количества попыток запроса.

## Повторная проверка после расширения allowlist (2026-08-22)

Владелец расширил Network access окружения до Custom с доменами из раздела
выше. Повторная проверка через прямой HTTP (curl) и через WebFetch:

| Источник | curl (сетевой egress сессии) | WebFetch | Вывод |
|---|---|---|---|
| cbr.ru / www.cbr.ru | ✅ `HTTP 200` | ❌ `EGRESS_BLOCKED` | доступен через прямой HTTP |
| moex.com → www.moex.com | ✅ `HTTP 301` → `HTTP 200` | не проверялся повторно | доступен через прямой HTTP |
| iss.moex.com (ISS API) | ✅ реальные рыночные данные получены (доска TQBR) | ❌ `EGRESS_BLOCKED` (первая попытка) | доступен через прямой HTTP, подтверждено содержимым |
| e-disclosure.ru / www.e-disclosure.ru | ⚠️ `HTTP 200`, но антибот-заглушка (см. ниже) | ❌ `EGRESS_BLOCKED` | сетевой блок снят, но сайт отдаёт защиту от ботов |

**Важное расхождение инструментов:** `WebFetch` продолжает возвращать
`EGRESS_BLOCKED` даже для cbr.ru после обновления allowlist, тогда как
`curl` из Bash проходит. Вывод: `WebFetch` не использует сетевую политику
этого окружения (Custom allowlist) — это отдельный, управляемый Anthropic
канал со своим, не настраиваемым из окружения списком доменов. Рабочий
инструмент для этого источника — прямой HTTP-запрос из Bash (`curl`), не
`WebFetch`. Это техническая деталь для дальнейшей работы, не вопрос к
владельцу.

### e-disclosure.ru: сетевой блок снят, но сайт защищён антиботом

`curl` с реалистичным `User-Agent` получает `HTTP 200` на `/`, `/poisk/`,
`/search/`, `/portal/`, но во всех случаях — один и тот же контент (~368 КБ):
HTML-заглушка со спиннером и `<noscript>`-редиректом на служебный путь
(`/exhkqyad`), то есть JS-проверка перед выдачей реального контента.
Путь `/api/` отдаёт `307` с `Set-Cookie: spid=…; spsc=…` (типичные
антибот-cookie для fingerprint/proof-of-work проверки) и редиректит сам на
себя — без исполнения JS-кода этот цикл не проходится.

Попытка обойти через headless-браузер (Chromium уже установлен в
окружении, добавлен пакет `playwright` временно через
`uv run --with playwright`, без изменения зависимостей проекта):
подключение через прокси окружения (`HTTPS_PROXY`) для Chromium даёт
`net::ERR_CONNECTION_RESET` — причём это воспроизводится и на cbr.ru,
который прекрасно открывается через `curl`. Значит, проблема не в
антиботе e-disclosure.ru, а в интеграции Chromium с прокси именно в этой
песочнице (другой сетевой стек/TLS-отпечаток, который прокси или сама
цель обрывает). Это не доказательство того, что headless-браузер не смог
бы пройти антибот e-disclosure.ru — вопрос остался неисследованным,
потому что браузер не смог подключиться вообще ни к одному сайту через
прокси этой сессии.

**Оценка, не факт:** дальнейшая отладка Chromium+прокси в этой песочнице
не гарантирует результата даже при успехе — антибот-провайдеры такого типа
часто дополнительно детектируют headless-браузеры (флаг
`navigator.webdriver`, TLS/JA3-отпечаток, репутация дата-центрового IP).
Обычный браузер под управлением человека (то есть локальная машина
владельца) проходит такую защиту естественным образом.

**Вывод:** применяю пункт 3 текущего задания по смыслу, а не по букве —
формально это не `403 host_not_allowed` (сеть открыта, отвечает сайт), но
результат для конвейера тот же: ни один доступный в этой сессии инструмент
не может получить реальный документ с e-disclosure.ru. Раз это первичный,
не заменяемый источник самих текстов предложений/требований о выкупе (в
отличие от cbr.ru/moex.com, которые дают справочные данные, но не тексты
существенных фактов), собирать документы с e-disclosure.ru предлагается
на локальной машине владельца (обычный браузер, вручную или обычным
скриптом без прокси-ограничений) и передавать в репозиторий тем же
способом, что и уже переданные `edge_thesis_R0_v1.md` /
`event_checklist_E1_v1.md` — с проверкой `sha256` и `published_at` перед
коммитом в `stage-E-1/documents/`.

Инвентарь (`inventory/events.jsonl`) остаётся пустым: строки по
voluntary_or_mandatory_offer, squeeze_out_request_95 и forced_buyback
структурно требуют текста самого предложения/требования (цена, ценовая
база, банк-гарант, приобретатель) — без e-disclosure.ru эти поля неоткуда
взять достоверно. `buyback_art_75_76` частично пересекается с решениями
Мосбиржи о делистинге (`www.moex.com/ru/news/?ncat=104`, реально доступен,
содержит формулировки о включении/исключении бумаг из Списка) — это
годится как триггер/наводка на конкретное событие, но не как источник
цены/условий выкупа, которые всё равно публикуются через раскрытие
информации. Ни одна строка не добавлена на основании одной лишь наводки
без первичного документа.

## Обновление 2026-08-23: headless-Chromium (таймбокс), cbr.ru, альтернативные агентства

### 1. Headless-Chromium через прокси — таймбокс исчерпан, брошено

Дополнительная диагностика (net-log Chromium): в одном и том же вызове
(один и тот же порт `HTTPS_PROXY`, одна и та же секунда) `curl` получает
`HTTP 200` на `www.cbr.ru`, а Chromium с тем же прокси — то `net::
ERR_CONNECTION_RESET`, то один раз явный ответ прокси `403 Forbidden:
"request blocked: no rule or allowlist entry allows host www.…"`.
Воспроизведено с отключённым preconnect/prediction, без
`--ignore-certificate-errors`, с `--proxy-server` вместо Playwright API —
результат тот же. Вывод: это несовместимость headless Chromium с
прокси-слоем именно этой песочницы (не антибот конкретного сайта — тот же
сбой на cbr.ru, который прекрасно открывается через `curl`). Не критический
путь, дальше не отлаживается; `curl` остаётся рабочим инструментом.
